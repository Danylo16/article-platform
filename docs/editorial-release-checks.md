# Перевірка перед передачею клієнту

Цей блок не виконує деплой і не змінює сховище медіа.

## Що змінилося

- Обкладинка: фокус X/Y для обрізаних прев’ю, три варіанти перегляду, alt, підпис, авторство; оригінальний файл зберігається. Повна стаття показує оригінал. Це не піксельне кадрування чи ретуш.
- Автор: завантаження/заміна/прибирання аватара, Instagram, заглушка з ініціалами при помилці фото.
- Картки: три рядки заголовка, три рядки опису, фіксовані місця для обкладинки та метаданих.
- Пошук `/search`: лише список опублікованих статей, усі слова запиту, пріоритет заголовка, 10 результатів на сторінку. Для поточного невеликого обсягу пошук виконується на web-сервері над списком API, без окремого індексу.
- Футер: реальні розділи, пошук, Instagram власниці, авторство розробки й LinkedIn. Юридичні сторінки та контактні реквізити власниці не вигадані й не додані.
- Build API копіює Prisma runtime у `dist/generated/prisma`, щоб зібраний API міг стартувати.

## Порядок перевірки

1. Зберегти резервну копію БД та каталогу `apps/api/uploads` перед першим production-релізом.
2. Виконати `yarn workspace api exec prisma migrate deploy`. Нова міграція лише додає поля, не переписує контент і фото.
3. Виконати збірки API/web, typecheck, lint і тести з команди передачі патча.
4. На локальному/тестовому середовищі завантажити аватар, зберегти автора, перезавантажити CMS та відкрити його опубліковану статтю. Перевірити Instagram.
5. Завантажити вертикальну й горизонтальну обкладинки. Змінити фокус, зберегти, перевірити картку, статтю, карту та повторне відкриття редактора.
6. Перевірити скасування прибирання фото, надто великий/пошкоджений файл та помилку API під час збереження.
7. Перевірити пошук: заголовок, автор, відсутній результат, наступна сторінка, Back у браузері; порівняти картки з короткими й довгими заголовками на 390/768/1440 px.
8. Для цільового домену налаштувати `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_API_URL`, `API_INTERNAL_URL`, `WEB_ORIGIN`, production-режим API. Публічні `NEXT_PUBLIC_*` значення задати до web build. Локальне сховище потребує постійного диска, що переживає перезапуски/релізи.
9. Перевірити вхід/вихід редактора, публікацію, медіа після перезапуску, sitemap і robots на цільовому домені. Без цих перевірок production-готовність не підтверджена.

Автоматичні тести схеми та логіки не замінюють браузерну перевірку і застосування міграції на реальній БД. У середовищі підготовки патча ці два пункти не виконувалися.
