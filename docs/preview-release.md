# Підготовка DORIDA до передрелізного запуску

Код підготовлено; розгортання, DNS, реальна БД, створення адміністратора та перевірка входу ще не виконані.
Працюємо лише з wip/current-state-2026-10-11. Commit/push — після явного дозволу власника.

## Безкоштовний варіант для огляду клієнткою

Попередній кандидат: Netlify Free (Next.js), Render Free (Fastify), Neon Free (PostgreSQL), окреме постійне сховище фото.
Netlify дозволяє комерційні проєкти, але Free має місячний ліміт кредитів і призупиняє сайт при його вичерпанні.
Render Free засинає через 15 хвилин; пробудження може займати близько хвилини. Локальний диск не зберігає uploads між деплоями/перезапусками.
Безкоштовний Render Postgres спливає через 30 днів — для наповнення клієнткою його не використовувати.
Neon Free на дату перевірки 21.10.2026 має 1 GB БД на проєкт і 100 CU-hours на місяць. Фото не зберігати в PostgreSQL.
R2 має безкоштовний ліміт Standard 10 GB-month та операцій; перевищення платне. Публічний r2.dev — лише для розробки, не остаточного production.
Не обіцяти повністю безкоштовний production: тарифи, ліміти, cold start і backup потрібно контролювати.
Vercel Hobby не підходить для цього комерційного клієнтського проєкту за умовами тарифу.
Цей блок НЕ переносить фото та НЕ створює зовнішні акаунти. Для безкоштовного API спершу налаштувати постійне сховище й перевірити upload після повторного деплою.

## Адреси і сесія CMS

Браузер звертається до API через ТОЙ САМИЙ домен сайту, шлях /backend. Це важливо: сервер Next.js читає cookie адміністратора на домені сайту.
Додано опційний rewrite /backend/:path* → API_PROXY_TARGET/:path*.
Приклад web-оточення (замінити всі домени на фактичні):

```
NEXT_PUBLIC_SITE_URL=https://YOUR-SITE.netlify.app
NEXT_PUBLIC_API_URL=https://YOUR-SITE.netlify.app/backend
API_INTERNAL_URL=https://YOUR-API.onrender.com
API_PROXY_TARGET=https://YOUR-API.onrender.com
SITE_INDEXING_ENABLED=true
```

API:

```
NODE_ENV=production
WEB_ORIGIN=https://YOUR-SITE.netlify.app
DATABASE_URL=<фактичний рядок підключення; секрет>
```

PORT підтримується сервером, за замовчуванням 3000. API_HOST — за замовчуванням 0.0.0.0 для PaaS.
Для VPS із локальним reverse proxy можна поставити API_HOST=127.0.0.1.
API_INTERNAL_URL має вести прямо до API без /backend. WEB_ORIGIN — точний origin без кінцевого слеша.
NEXT_PUBLIC_* і rewrite/header-конфіг фіксуються під час build: зміна потребує rebuild. SITE_INDEXING_ENABLED задавати однаково під час build і runtime.
Сесії, Set-Cookie та multipart через proxy ОБОВ'ЯЗКОВО перевірити на вибраному хостингу; локальна збірка не гарантує поведінку адаптера Netlify.

## Фото

Для сервера з постійним диском:
- MEDIA_STORAGE_DRIVER=local
- UPLOAD_DIR=/srv/dorida/shared/uploads

Шлях має існувати, бути доступним API й лежати поза каталогами релізів. Той самий шлях використовується для запису та /uploads.
Скопіювати наявні apps/api/uploads до нього до перемикання. Не видаляти єдину вихідну копію.
На Render Free локальний режим НЕ дозволяє безпечно почати наповнення. Наявний s3-драйвер у проєкті можна налаштувати окремо; старі /uploads-посилання також потребують міграції, включно з Markdown, обкладинками й аватарами.

## Створення клієнтського адміністратора

Команда PowerShell із кореня репозиторію:

```
& .\scripts\create-dariia-admin.ps1
```

Вона запускає наявний admin:create для dariia.skrypnyk.sd@gmail.com. Пароль вводиться приховано (15–128 символів), не записується в код і не передається аргументом CLI.
Важливо: запис створюється в БД, заданій DATABASE_URL для цього процесу або apps/api/.env. Створення локального запису НЕ створить його в Neon.
Для хмарної БД використати її секретний DATABASE_URL лише в локальному оточенні запуску, не в чаті, не в репозиторії. Після виконання повернути локальне підключення.
Існуючий запис не перезаписується. Якщо він уже є, перевірити вхід; не скидати пароль автоматично.
У Linux: тимчасові ADMIN_BOOTSTRAP_EMAIL, ADMIN_BOOTSTRAP_PASSWORD → yarn workspace api admin:create → видалити тимчасові змінні. Не залишати bootstrap-пароль у runtime-env сервісу.
Повідомлення клієнтці цей блок не надсилає.

## Послідовність запуску

1. Зафіксувати перевірений стан у Git після дозволу; зберегти попередню версію для відкату.
2. Backup БД і фото. Не запускати demo seed у клієнтській БД.
3. Node 24, Yarn 4.18.0; yarn install --immutable.
4. yarn workspace api exec prisma migrate deploy (без reset).
5. API build, web typecheck/lint/build, тести, git diff --check.
6. Розгорнути на службових піддоменах провайдерів. Власний домен для preview не потрібен.
7. Створити адміна в потрібній БД та перевірити сценарії нижче.
8. Для справді закритого preview потрібен контроль доступу на рівні хостингу/proxy, який охоплює і API. noindex не є паролем. Без такого контролю сайт доступний за посиланням; конфіденційні матеріали не публікувати.

## Приймальна перевірка

- /health перевіряє процес; /ready перевіряє доступність БД (200/503).
- Login, reload CMS, logout, 401 на /admin/articles без сесії, відхилення чужого Origin при зміні даних.
- Чернетка → фото → збереження → перевідкриття → публікація → зняття з публікації.
- Draft відсутній у публічних статтях, пошуку та sitemap.
- Обкладинка, inline-фото, аватар працюють ПІСЛЯ перезапуску та нового деплою.
- Видиме місце без статті доступне; прихований тип виключає свої місця з публічної карти.
- Створений у CMS новий розділ відкривається за slug, має canonical і метадані.
- Мобільні розміри 390/768/1440 px, меню, пошук, клавіатура, error/loading, незбережені зміни.
- Не передавати клієнтці сайт як стабільний, доки ці сценарії не пройдені на реальному хостингу.

## Backup і відкат

scripts/backup-release.sh — для Linux із ЛОКАЛЬНИМ постійним uploads. Потрібні Node, pg_dump сумісної з сервером версії, tar, sha256sum, DATABASE_URL, UPLOAD_DIR, BACKUP_DIR.
На час копії призупинити записи API, щоб БД і фото відповідали одне одному. Копію виносити поза сервер; для S3/R2 потрібен окремий backup об'єктів.
Автоматичний щоденний запуск і сповіщення про помилки ще треба налаштувати на вибраній інфраструктурі.
Перевірка відновлення: ОКРЕМА порожня БД + ОКРЕМИЙ каталог фото; pg_restore --exit-on-error --no-owner --no-privileges, потім перевірка статті й фото на тестовому екземплярі.
Не відновлювати поверх клієнтської БД. Архіви містять приватні дані; обмежити доступ.
Відкат коду — попередній артефакт релізу; БД і фото залишаються спільними. Сумісність міграцій перевіряти до відкату. Автоматичного rollback БД немає.

## SEO

Додано canonical, Article/WebSite JSON-LD, Open Graph/Twitter, соціальну заставку, favicon, коректні дати sitemap, підтримку нових розділів CMS.
SITE_INDEXING_ENABLED=false за замовчуванням: robots disallow /, X-Robots-Tag noindex та порожній sitemap. CMS і пошук залишаються noindex і на публічному сайті.
Rubrik-фільтри канонізуються до основної сторінки. Статті використовують реальний updatedAt, без вигаданого оновлення при кожному запиті.
Публічний запуск: фінальні URL, SITE_INDEXING_ENABLED=true, rebuild/restart; перевірити відсутність загальної заборони індексації, canonical, sitemap, Rich Results Test і Search Console.
До індексації прибрати тестові публікації, погодити Impressum/Datenschutz/контакти, перевірити Lighthouse на реальному домені.
SEO-розмітка не гарантує позиції. Редакційні SEO-поля та оптимізація розмірів зображень — наступний блок; безпідставних оцінок PageSpeed тут немає.
